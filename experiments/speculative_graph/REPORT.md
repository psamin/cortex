# Learning to Speculate: graph-based predictive execution (experiment 2): results

Design, variants, and safety mechanisms are in [DESIGN.md](DESIGN.md). All runs used GT Futurama GPUs. Every number below is regenerated by `report/build.sh` from the listed run directories. **Measured facts and interpretation are kept in separate paragraphs.**

## Answers up front
| Question | Measured answer |
|---|---|
| **H1** Are execution transitions predictable beyond chance and frequency baselines? | **Yes.** MiniGrid: top-1 accuracy 0.60 for the context-conditioned predictor, vs 0.38 frequency, 0.34 uniform, 0.48 hand-written heuristic (held-out test trajectories, N = 2,906 decisions). Coding: `edit → run_tests` and `run_tests → run_tests` dominate, and frequency already captures them. |
| **H2** Does predictive execution cut critical-path latency? | **Yes in both tracks, with a large difference in cost-effectiveness.** Coding agent: **−15 to −21% task wall-clock** for learned top-1/utility and −25% for run-everything (paired, 30 held-out tasks, identical decisions). MiniGrid LLM-call prefetch: **−7.4% decision latency** (B5, p=0.028) at **+107% model compute**. Heuristic or random prefetch made decisions **slower** (+6.7%, +13.1%). |
| **H3** Does budget-aware scheduling beat always-top-K? | **Yes.** MiniGrid: speculating all 3 actions made decisions **47% slower** (contention) at 6× compute, while top-1 and utility were faster. Coding: running every eligible tool saved the most time, but learned top-1 got about 85% of that saving with a third of the launches and almost no wasted work. |
| **H4** Does personalization beat a global model? | **Mixed.** Within one workflow, shrinkage personalization equals the global model (top-1 0.600 vs 0.600; matched k=10: 0.550 vs 0.544). **Across workflows, matching history matters a lot:** for the SSD agent, a predictor trained on another workflow (8b greedy) reached a 0.46 hit rate and +2.2% latency (n.s.); trained on the SSD agent's own history it reached 0.68 hits and **−5.8% latency (p<0.001)**. |
| **H5** Is SSD + predictive execution better than either alone? | **Yes, on two axes.** Graph-ranked rollout candidates (B7) let SSD use 2 branches instead of 3 at equal success, and cut compute 53% vs LLM-ranked K=2 (p<0.001), because the predictor keeps the action SSD would choose in the candidate set. For latency at equal success: The corrected B8 (SSD + workflow-matched prefetch) kept success at 1.00 (same as SSD) and cut decision latency 2.261 → 2.130 s (−5.8%, paired p<0.001) at +35% model compute. SSD alone is what lifts success from 0.45 to 1.00 over B0, which no amount of prefetching does. |
| Replace SSD with graph speculation? | **No. Keep both, as separate layers.** They target different things: SSD improves *decisions* (success 0.17 → 1.00), while predictive execution only reduces *latency* at equal decisions. Combine them where the agent waits on slow tools. |

## 1. Track A: MiniGrid, prefetching the actor's next LLM call
**Setup.**
- Actor: qwen3:8b greedy (B0).
- Predictors are trained on validation trajectories (seeds 1000–1049, 1,892 decisions) and frozen. Evaluation uses test seeds 10000–10019, cache off.
- H200, 2 concurrent episodes (low contention).
- `report/data/specgraph_latency/latency_paired.md`

**Facts.**
- With 60% hit accuracy, prefetching cut mean decision latency by 7% and roughly doubled model compute.
- Most hits are *late*: the prefetched call was still running when needed, so only part of its duration was saved.
- Prefetching every action reaches 92% hits but is much slower, because three concurrent calls slow each other down.
- Success rates vary (0.30–0.55 on 20 seeds) even though the actor is the same. This reflects temperature-0 server nondeterminism under different batching, not a policy change. The CIs on 20 seeds are wide.

**Interpretation.**
- Here the "work" being pre-executed is a GPU call that competes with the critical-path call for the same GPU. So the achievable saving is bounded both by hit rate and by contention.
- The 4b/8b latency equality (see the main report, §5) means that only a near-free guesser, like the learned predictor here, can work at all.

## 2. Track B: coding agent, pre-executing tools on immutable snapshots
**Setup.**
- 30 held-out bug-fix tasks, each a distinct package (with 30 more for training history).
- The qwen3:8b agent chooses every operation.
- Tools are real `pytest`, `ruff`, and an import check, run in isolated copies.
- Every policy replays the reference run's LLM responses and think durations, so decisions are identical and only scheduling differs; `same op sequence` verifies this.
- L4 GPU. `report/data/codebench/codebench_summary.md`

| Policy | Success | Task wall-clock s (mean [95% CI]) | Δ vs none, paired [95% CI] | Tool s on critical path | Launched (reused / late / unused) | Speculative CPU-s | Wasted CPU-s |
|---|---|---|---|---|---|---|---|
| none | 1.00 | 16.17 [13.46, 20.20] | — | 5.93 | 0 | 0 | 0 |
| memo (dedupe identical requests, no prediction) | 1.00 | 13.55 | −2.62 [−4.90, −1.13] | 3.19 | 0 | 0 | 0 |
| all eligible tools (ordinary parallelism) | 1.00 | 12.06 | **−4.11 [−6.42, −2.69]** | 1.77 | 204 (3 / 63 / 138) | 52.2 | 4.6 |
| random tool | 1.00 | 12.62 | −3.54 [−5.75, −2.12] | 2.25 | 111 (0 / 32 / 79) | 18.3 | 2.4 |
| learned top-1 (frequency) | 1.00 | 12.72 | −3.45 [−5.78, −2.00] | 2.42 | 68 (3 / 63 / 2) | 48.5 | 1.0 |
| learned top-1 (global context) | 1.00 | 12.89 | −3.28 [−5.62, −1.86] | 2.62 | 68 (3 / 63 / 2) | 48.5 | 1.0 |
| learned top-1 (personalized) | 1.00 | 13.73 | −2.43 [−4.92, −0.72] | 3.35 | 70 (3 / 65 / 2) | 49.6 | 1.0 |
| utility (personalized) | 1.00 | 13.29 | −2.88 [−5.24, −1.44] | 3.03 | 68 (3 / 63 / 2) | 48.5 | 1.0 |

**Noise floor:** all four learned policies launched essentially the same work (about 68 `run_tests` pre-runs, since `run_tests` is the only read-only op worth predicting). Their 1 s spread in mean wall-clock is therefore run-to-run timing noise. The predictors can't be ranked against each other in this benchmark; only "learned top-1 vs none / all / random" is resolved. Repeated timing runs would narrow this.

**Facts.**
- Pre-executing tests removed most tool time from the critical path: 5.9 s down to 1.8–2.4 s per task.
- Most of the saving comes from overlapping the test run with the next LLM "think". Reuses are mostly *late*: the agent's think, about 1 s, is shorter than a test run, about 1 s.
- Memoization alone recovered 44% of tool time, because the agent often re-runs tests on an unchanged snapshot.
- Among the predictive policies, learned top-1 wasted almost nothing (2 of 68 launches). "Run everything" saved about 0.7 s more per task but wasted 138 of 204 launches.

**Ablation J (prediction vs ordinary parallelism).** Parallelism over known-independent tools (`all`) gives the largest latency cut. Prediction buys efficiency: about 3× fewer launches and about 5× less waste for about 85% of the saving.

## 4. Safety and correctness validation
Tests in `tests/test_specgraph.py` and `tests/test_codebench.py` cover:
- Lossless reuse under a perfect predictor.
- Invalidation and fallback under a wrong predictor.
- No launches under `none`.
- A stale model fingerprint is never reused.
- A stale workspace snapshot is never reused, and is counted as wasted.
- Speculative work never touches the real workspace (isolated copies).
- A hanging tool times out cleanly. This came up in practice: one injected bug creates an infinite loop.

## 5. Threats to validity
- **Simulator access in Track A:** the predicted next observation comes from a clone that shares the real RNG. In production, this corresponds to a side-effect-free environment API. Without one, Track A prefetching is impossible.
- **Replay design in Track B:** think times are replayed from a single reference run, so LLM latency variance is excluded by construction. A real deployment adds that variance to both arms.
- **Small N:** Track A has 20 test seeds and Track B 30 tasks × 1 repeat. CIs are reported, and the Track A latency gain is significant only for B5.
- **Personalization had little to work with** (single environment per track). H4 is untested in the multi-environment sense that motivates it.
- **Server nondeterminism** at temperature 0 makes the MiniGrid "same actor" arms differ in outcomes.

## 6. Decision (spec §19)
| Criterion | Track A (LLM-call prefetch) | Track B (tool pre-execution) |
|---|---|---|
| Latency under equal budget | small gain (−7%) at +107% compute; hybrid −5.8% at +35% | large gain (−15 to −21% for learned top-1, −25% run-everything) at ~1.6 CPU-s per task |
| Success preserved | yes, up to server nondeterminism | yes (identical, 30/30) |
| Resource use | poor | good with learned top-1 |
| Benefits from history | yes (frequency → context) | weak (frequency ≈ context) |
| Gain beyond plain async execution | n/a | no for raw latency; yes for efficiency |

**Recommendation:** keep SSD (decision speculation) and graph-based predictive execution as **separate, composable layers**. Use predictive execution for slow, side-effect-free tools (tests, lint, builds) where it removes real work from the critical path. Don't use it to prefetch LLM calls on the same GPU unless the actor is much slower than the guess and there is spare capacity.
